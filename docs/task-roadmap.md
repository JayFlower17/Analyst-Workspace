# 任务路线文档

## 1. 文档目标

本文档基于项目的目标形态来拆解后续执行路线。

路线设计原则：

1. 先收敛主线，再扩展能力
2. 每个 Phase 都能独立产出可见结果
3. 每个任务尽量足够小，适合快速完成
4. 优先做能降低后续复杂度的任务

项目目标形态：

**围绕 workspace 统一组织结构化数据、非结构化文档和历史分析资产，通过 agent 编排完成可执行、可追溯、可复用的数据分析。**

---

## 2. 执行规则

### 2.1 任务粒度规则

每个任务都应尽量满足下面条件：

- 单个任务目标清晰
- 能在较短时间内完成
- 验收标准明确
- 完成后可以单独提交

### 2.2 优先级规则

优先顺序固定为：

1. 主流程可用性
2. 架构收口
3. 能力扩展
4. 体验优化

### 2.3 范围控制规则

如果某个任务涉及多个系统层，优先拆开，不把前端、后端、agent、harness 混成一个大任务。

#### Task 2.1.2

设计文档分块实体模型

验收标准：

- 至少包含 chunk ID、document ID、chunk text、顺序号、metadata

#### Task 2.1.3

设计文档处理状态字段

验收标准：

- 能区分上传成功、解析中、解析失败、已索引

## Phase 3：构建结构化 + 非结构化联合上下文层

### Phase 目标

让系统能围绕同一个问题，同时使用表格数据和文档知识。

核心结果：

- 上下文构建不再只有 schema
- 可以同时召回表、描述、关系、文档 chunk
- 为 agent 提供统一上下文包

---

### 3.1 上下文模型设计

#### Task 3.1.1

定义 `StructuredContext` 数据结构

验收标准：

- 包含表、字段、关系、统计信息

#### Task 3.1.2

定义 `DocumentContext` 数据结构

验收标准：

- 包含文档片段正文、来源文档、chunk metadata

#### Task 3.1.3

定义 `SemanticContext` 数据结构

验收标准：

- 包含 workspace 描述、表描述、业务口径等

#### Task 3.1.4

定义 `UnifiedAnalysisContext` 数据结构

验收标准：

- 能统一封装 structured/document/semantic 三类上下文

---

### 3.2 Context Assembler 服务

#### Task 3.2.1

新建上下文装配服务骨架

验收标准：

- 有单独模块或单独 service 承担上下文组装

#### Task 3.2.2

先接 structured context 组装

验收标准：

- 不影响原有 workspace schema 逻辑

#### Task 3.2.3

接入 semantic context 组装

验收标准：

- workspace 描述和表描述能进入统一上下文

#### Task 3.2.4

接入 document retrieval

验收标准：

- 可根据 query 检索 workspace 内相关 chunk

#### Task 3.2.5

组合成统一 prompt 载荷

验收标准：

- 输出格式稳定
- 不同上下文块边界清晰

---

### 3.3 检索策略

#### Task 3.3.1

定义 query 到 document retrieval 的触发规则

验收标准：

- 不是所有问题都盲目检索文档

#### Task 3.3.2

定义 query 到 structured retrieval 的触发规则

验收标准：

- 表上下文可按 focusDatasetIds 或 workspace 范围收缩

增加 topK 和截断策略

验收标准：

- prompt 长度可控

#### Task 3.3.4

验收标准：

- 后续 agent 和 reporter 能知道信息来自哪里

### 3.4 第一批联合问题验证

#### Task 3.4.1

准备首批“表 + 文档”联合问题集

验收标准：

验收标准：

#### Task 4.1.3

#### Task 4.2.3

- planner 输出不是自由文本，而是结构化计划
