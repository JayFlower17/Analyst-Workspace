# 第 2 章 需求分析

## 2.1 系统目标

本系统的总体目标是设计并实现一个基于 AI 智能体的交互式数据分析平台，使用户能够以自然语言方式完成对结构化数据与非结构化文档的联合分析，并通过工作区机制持续组织和沉淀分析过程。

具体而言，系统需要实现以下目标：

1. 支持用户以自然语言发起分析请求，降低传统 SQL 驱动分析方式的使用门槛。
2. 支持上传和管理结构化数据文件，使数据能够被系统转换为可执行分析对象。
3. 支持上传和管理非结构化文档，使业务规则、说明文本和参考资料能够参与分析过程。
4. 支持通过工作区统一组织数据表、文档和分析结果，为持续分析提供上下文环境。
5. 支持保存分析结果，使其成为可回看、可复用的分析资产。

## 2.2 功能需求分析

### 2.2.1 问答模块需求

问答模块是系统面向用户的快速分析入口，主要满足探索式、轻量级分析需求。用户可以直接在问答界面输入问题，由系统自动理解问题并生成分析结果。

该模块应具备以下功能：

1. 支持创建和切换聊天会话。
2. 支持在问答过程中上传结构化数据文件。
3. 支持将特定数据集挂载到当前问答上下文中。
4. 支持基于当前会话内容发起数据分析。
5. 支持查看分析摘要、结果表格和生成的 SQL 或 Python 代码。
6. 支持将当前问答会话一键升级为工作区，以便后续继续开展正式分析。

### 2.2.2 工作区模块需求

工作区模块是系统的正式分析阵地，用于承载多数据集、多文档和多轮分析的持续性工作流。与问答模块相比，工作区更强调上下文组织和分析沉淀。

该模块应具备以下功能：

1. 支持创建和管理工作区。
2. 支持将多个数据表纳入同一工作区。
3. 支持挂载文档资产，并使其参与工作区分析。
4. 支持维护数据表之间的关系信息，为多表分析提供结构依据。
5. 支持在工作区范围内发起正式分析请求。
6. 支持查看分析结果、执行代码和历史分析记录。

### 2.2.3 数据仓模块需求

数据仓模块是系统中全部资产的统一管理入口，用于对系统中的核心对象进行总览和维护。其角色不是发起分析，而是对分析所依赖的资产进行集中管理。

该模块应具备以下功能：

1. 支持查看全部结构化数据表。
2. 支持查看全部非结构化文档。
3. 支持查看全部工作区对象。
4. 支持查看全部分析结果资产。
5. 支持按名称、范围和归属关系检索各类对象。

### 2.2.4 文档处理与检索需求

由于本系统需要实现结构化与非结构化联合分析，因此文档处理模块必须支持从多种文件类型中提取文本内容，并为后续检索与分析提供基础。

该模块应具备以下功能：

1. 支持 TXT、Markdown、PDF 和 DOCX 文件上传。
2. 支持自动提取文档正文。
3. 支持将长文档切分为多个 chunk。
4. 支持记录文档处理状态。
5. 支持在工作区范围内根据用户问题检索相关文档片段。

### 2.2.5 分析执行与结果沉淀需求

系统的核心价值在于将用户问题转换为可执行分析过程，并将结果以可理解、可保存的方式返回给用户。

该模块应具备以下功能：

1. 支持根据用户问题生成 SQL 或 Python 分析逻辑。
2. 支持对结构化数据执行查询和计算。
3. 支持结合文档上下文对分析结果进行补充解释。
4. 支持返回结果表格、摘要和执行代码。
5. 支持将分析结果保存为 artifact，以便后续回看与复用。

## 2.3 非功能需求分析

### 2.3.1 可用性需求

系统应具备较好的交互性，使用户能够以低学习成本使用主要功能。前端界面应尽量简洁，减少无关说明文字，突出问答、工作区和数据仓三大核心模块。

### 2.3.2 可扩展性需求

系统需要支持后续扩展新的分析能力，例如更复杂的智能体编排流程、更完善的检索增强策略以及更丰富的结果可视化能力。因此，系统应采用模块化设计，保持前后端职责边界清晰。

### 2.3.3 性能需求

系统在一般数据分析场景下，应能够在合理时间内完成上传、解析、检索和分析请求。对于中小规模数据集和常规分析问题，系统应具备较好的响应速度，以满足交互式使用要求。

### 2.3.4 可维护性需求

系统需要在后续开发与论文完善过程中便于维护与修改，因此应将数据集管理、工作区管理、文档处理、分析执行和评测验证等模块尽量解耦，并提供文档说明支持持续迭代。

### 2.3.5 安全性需求

系统应避免执行高风险 SQL 或不受控代码。对于 SQL 应设置白名单限制；对于 Python 执行应设置受限环境、超时与隔离机制；对于认证信息和密钥配置应避免硬编码在公开仓库中。
